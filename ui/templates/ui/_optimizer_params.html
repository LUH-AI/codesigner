{% load i18n %} {% comment %} One optimizer's settings, as a bordered panel — the same `check-group` box the figures checkboxes live in. It carries number inputs and selects rather than checkboxes, which the box already supports: the "Run until…" stopping criteria on the experiment page are the same fieldset. Nothing here names an optimizer. The fields come from what the optimizer declares in its `params_schema`, so a new setting is one line in `core` and this template does not change. An optimizer that declares nothing renders nothing. `panel_disabled` renders the fieldset inert, which disables every control in it without touching them one by one. The create page uses it so an unchosen optimizer's settings are never submitted even with no JavaScript running; pages showing a single panel leave it unset. An empty numeric field means "whatever the strategy does by default", the same convention the stopping criteria use — the strategies disagree about several of these, so imposing one number on both would be worse than saying nothing. A setting can declare that it only applies when another one has a certain value (`depends_on`), which arrives here as `data-when="name=value"`. The script at the bottom hides those, and hides them only: a disabled field is not submitted, and switching search strategy would then throw away everything set for the other one. The names do not collide — they are prefixed per strategy — so there is nothing to gain by dropping them. {% endcomment %} {% if optimizer_params %}
